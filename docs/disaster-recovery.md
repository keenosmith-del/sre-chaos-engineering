# Isolated PostgreSQL recovery drill

`make backup` creates a pg_dump custom-format artifact in a named backup volume. The runner holds a repeatable-read transaction, exports its snapshot, reads the transaction watermark/state counts in that snapshot, and gives that same snapshot to pg_dump. Metadata records timestamp, database, snapshot, format, bytes, SHA-256 and watermark evidence. This avoids comparing a dump with an unrelated later live query.

`make restore-verify` verifies existence/checksum, recreates only `recovered` on the separate recovery-postgres container, and restores with pg_restore --exit-on-error --no-owner --no-privileges. It verifies restored schemas via business queries, exact snapshot order/terminal/outbox/delivery counts and watermark, negative stock, confirmed payment/reservation relationships, cancelled reservation release and outstanding transactions. Active application commerce is never replaced.

The committed-order creation timestamp watermark is compared with the live database; RPO seconds are the live maximum created_at minus the restored maximum, and lost_order_count records the count difference. This is a recoverable order-record watermark, not a guarantee that later transitions on older orders are captured. Snapshot state comparisons verify the dump's own data. The backup can faithfully restore incomplete sagas; such a result is reported as not fully business-consistent until reconciliation, never a successful completed recovery.

Restore-drill RTO begins at the declared isolated restore operation and ends at verified restored database state. It measures backup restoration, not an application service outage. Experiment reports separately record fault-injection-to-consistency time and cleanup-to-verification time. Local demonstration objectives default to 120-second RTO and 300-second RPO, configurable in .env through Compose. They are not production guarantees. The API reports the objective comparison and measurement scope explicitly.

PostgreSQL-only backup excludes Redis, RabbitMQ queued/dead-lettered messages and Jaeger data. Published outbox rows can be present while worker projection is absent; restoring PostgreSQL alone does not restore the corresponding broker event. Retain/replay broker events or explicitly reset selected outbox publication state under a recovery plan after proving consumer idempotency. The default drill intentionally does not attach restored state to active consumers or claim coordinated recovery.

Runbook: stop new fault jobs; allow reconciliation/backlog to drain; create backup; run isolated restore; inspect checksum, snapshot_matches, restored consistency, RTO/RPO/objective; retain the artifact/evidence; restart load only after verification. If verification fails, preserve evidence and investigate. Do not run pg_restore against the active commerce database. Backup artifacts are locally retained as latest.dump/latest.json; retention/encryption are future production work.
